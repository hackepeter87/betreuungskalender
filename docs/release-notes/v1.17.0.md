# v1.17.0

`v1.17.0` completes the link-based onboarding workflow for native OIDC
installations. It improves invitation delivery, makes setup and invitation
links understandable before sign-in, and preserves existing membership and
group-based authorization during upgrades.

## Highlights

- Owner setup and invitation links now open a neutral landing page before the
  browser continues to authentication.
- Invalid, expired, revoked, and already-used links show a clear error instead
  of a raw API response.
- Settings shows the invitation email option only when email delivery is fully
  configured. Entering a recipient address selects delivery by default.
- Normal login no longer receives a provisional role merely because first-use
  setup is incomplete.
- The onboarding guide now documents the mounted owner secret, invitation
  lifecycle, app memberships, OIDC group fallback, and safe upgrade order.

## Authorization compatibility

Authorization continues to resolve in this order:

1. An active application membership.
2. A configured OIDC group role when no app membership exists.
3. Access is rejected when neither source grants a role.

The only exceptions are validated owner-setup and invitation contexts. They
may create the specific owner or invited membership after a validated OIDC
callback. A normal login cannot use incomplete setup to bypass role checks.

Existing installations keep their memberships, group fallback, invitations,
sessions, and owner compatibility behavior. No existing deployment must reset
authorization during this update.

## Fresh owner setup

For a fresh native OIDC installation, generate a random value outside the
repository, mount it read-only at `OWNER_SETUP_TOKEN_FILE`, and open the
one-time `/setup?token=...` URL before `OWNER_SETUP_TOKEN_TTL_SECONDS` expires.
The link claims the authenticated user as owner; the setup wizard then remains
responsible for required app data.

The standard Compose example does not force this secret mount on existing
installations. Follow [Self-hosted onboarding and member administration](../self-hosted-onboarding.md)
for the mount and verification steps.

## Invitation email delivery

Manual invitation codes remain available. To enable email delivery, configure
all of the following:

```dotenv
INVITATION_EMAIL_ENABLED=true
INVITATION_PUBLIC_BASE_URL=https://betreuung.example.net
SMTP_HOST=smtp.example.net
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=no-reply@example.net
```

`SMTP_FROM` is the sender mailbox accepted by the SMTP relay. When the
installation has a label, the app uses that label as the sender display name.
Secrets and real domains must remain in private deployment configuration.

## Security notes

- Owner setup and invitation values remain one-time bearer secrets.
- SQLite stores hashes rather than raw onboarding values.
- Request logging redacts setup, invitation, continuation, and OIDC callback
  query strings.
- OIDC state, nonce, PKCE, issuer, audience, cookie, expiry, revocation, and
  single-use protections remain enforced.
- Landing and error pages do not include bearer values in error text.

## Validation

The release is validated with lint, unit and integration tests, production
build, browser tests, runtime security tests, strict release checks, container
validation, CodeQL, and release artifact checksum verification.
