# v1.20.0

`v1.20.0` adds a maintained Helm deployment option for running the
Betreuungskalender application on Kubernetes.

## Highlights

- The chart supports image selection, ingress and TLS, persistent storage,
  health probes, resources, scheduling constraints, and additional labels and
  annotations.
- Runtime configuration is supplied through values, ConfigMaps, and references
  to existing Secrets. Credentials do not need to be stored in chart values.
- Security defaults align with the release image: non-root execution, dropped
  Linux capabilities, privilege escalation disabled, and a read-only root
  filesystem.
- CI and release validation lint and render the chart and verify that its
  application version matches the release.

## Storage and availability model

Each Helm release uses its own persistent volume for the SQLite database. The
chart supports exactly one application replica and the `Recreate` deployment
strategy. This avoids presenting horizontal scaling guarantees that the
embedded database cannot provide safely.

The storage class must provide reliable POSIX locking. Keep `/data` persistent.
Enable the separate backup claim when in-application backups must survive pod
replacement, and copy verified backups outside the installation's failure
domain using an independently managed process.

## Configuration and upgrade

Start with `charts/betreuungskalender/examples/native-oidc-values.yaml`. Replace
all placeholder values, reference existing Kubernetes Secrets for credentials,
and configure the exact external HTTPS origin for browser and OIDC settings.

Before upgrading, create and verify a current backup. Render and review the
effective chart, run the upgrade with readiness waiting enabled, then execute
the Helm test and application runtime verification. A Helm rollback does not
reverse database migrations; use a compatible verified backup when a database
downgrade is required.

See [Kubernetes deployment with Helm](../deployment-helm.md) for the full values
reference, installation steps, storage constraints, health checks, and upgrade
procedure.

## Existing installations

No database migration or application configuration change is introduced by
this release. Existing Compose and direct-container deployments remain
supported. Moving an existing installation to Kubernetes requires a planned,
verified transfer of its SQLite database and backup data; do not start both
deployments against the same database volume.

## Validation

The release is validated with linting, unit and integration tests, the
production build, Helm lint and render checks, runtime security tests, container
smoke tests, browser tests, strict release checks, and release artifact
validation.
