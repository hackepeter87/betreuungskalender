# v1.19.0

`v1.19.0` introduces workspace-scoped permissions for installations where
multiple people collaborate in one Betreuungskalender.

## Highlights

- Fixed roles keep access understandable: owner, admin, editor, scheduler, and
  viewer.
- The server enforces a named permission for every protected API route.
- Schedulers and viewers receive reduced child, caregiver, and appointment
  responses instead of full records that would need browser-side filtering.
- The owner can invite members, change their role, and revoke their access.
- Scheduler writes are restricted to future planned appointments for assigned
  caregivers and cannot include sensitive details.

## Existing data and migration

Database migration `028_workspace_permissions.sql` maps existing memberships
without deleting their history:

- `admin` remains `admin`;
- `parent` becomes `editor`;
- `readonly` becomes `viewer`.

Known active users without any membership history receive a compatible
membership. A previously removed membership is never reactivated. Once an
installation owner exists, an authenticated identity without an active
membership has no workspace access.

Existing care data, OIDC identities, active-user calendar feeds, backups, and
accepted or revoked invitation history remain compatible.

## Access removal

Removing a workspace member takes effect on the next API request. The same
transaction also revokes that member's personal calendar-feed tokens, disables
push subscriptions, and removes pending confirmation requests. An existing
OIDC login session does not restore workspace access.

Role and care-party assignment changes are evaluated on every protected
request. Access that no longer belongs to the current role is not retained by
an older personal feed or confirmation task. Resetting domain data preserves
the installation owner while reopening the guided domain setup.

## Configuration

No new environment variable is required. Existing OIDC and trusted-proxy group
mapping remains available before an owner is established. After owner setup,
manage access through the fixed workspace roles in the application.

Update release references to `1.19.0` and keep existing data and backup mounts
writable by the container user.

## Validation

The release is validated with migration and permission-matrix tests, restricted
response tests, scheduler boundary tests, browser checks on desktop, iPhone,
and iPad, the production build, runtime security tests, strict release checks,
and release artifact validation.
