# v1.27.0

`v1.27.0` establishes a backend-neutral persistence boundary while retaining
SQLite as the only supported and default database for the self-hosted
application.

## Persistence boundary

- Persistence drivers now expose explicit lifecycle, migration, transaction,
  health, and query boundaries.
- Identity, workspace, calendar, reporting, portable transfer, and operational
  services use the asynchronous SQLite runtime instead of opening independent
  database connections.
- SQLite remains the sole supported runtime. This release does not add a new
  database option, deployment mode, or database configuration variable.
- Existing API behavior, authentication modes, backup files, and portable
  transfer packages remain compatible.

## SQLite upgrade assurance

- A checksum manifest records every migration released through `v1.26.1`.
- Upgrade tests create an isolated `v1.26.1` database, seed fictional domain
  records, open it with the current runtime, and verify preserved data and the
  current migration sequence.
- The parity suite also checks representative reads and writes, foreign-key
  enforcement, transaction rollback, SQLite integrity, and repeated migration
  execution.
- Released migration files are immutable. Future schema changes must append a
  new migration and extend the manifest without rewriting the historical
  checksums.

## Dependency maintenance

- Fastify is updated to the patched `5.12.x` line.
- Transitive URI-validation dependencies are updated to patched releases.
- Application routes, validation policy, and public error responses are
  unchanged.

## Compatibility and upgrade

No new database migration is introduced by the release itself. Existing
SQLite installations are opened and migrated through the same ordered files as
before. Operators should retain a verified backup before every update and keep
the database on storage that supports POSIX file locking.

The Helm chart is updated to `0.8.0` with application version `1.27.0`.

## Validation and rollout

The release is validated with type checks, unit and integration tests, browser
tests, runtime-security checks, container and Helm smoke tests, SQLite
upgrade-parity checks, CodeQL, image validation, dependency auditing, and the
strict release check. Only the `testing` channel is updated for manual
acceptance. `production` and `latest` remain unchanged.
