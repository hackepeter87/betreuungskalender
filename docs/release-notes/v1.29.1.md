# v1.29.1

`v1.29.1` aligns security boundaries across the self-hosted application's
registered routes, workspace actions, trusted-proxy mode, and request budgets.

## Authorization and workspace actions

- Protected API routes retain their declared authorization policy for every
  supported request-target form.
- Care-conflict preview and resolution use the same workspace permissions and
  assignment boundaries as the affected care entries.
- Existing owner, admin, editor, scheduler, and viewer capabilities otherwise
  remain unchanged.

## Trusted proxy authentication

- Trusted-proxy mode requires an explicit source allowlist.
- Authenticated requests require the configured stable identity-subject header.
  Display names and email addresses remain presentation attributes and do not
  establish durable identity.
- Current Compose, Helm, configuration, security, and update guidance describes
  the required proxy boundary.

## Request budgets

- Explicit route-specific limits take precedence over central defaults.
- Authentication, recovery, owner setup, invitation acceptance, import, and
  migration workflows use the configured sensitive request budget.
- Ordinary reads, writes, exports, calendar feeds, and intentionally public
  information pages retain their designated policies.
- Limit responses remain generic and contain no request or identity details.

## Compatibility and update

The Helm chart is `0.10.1` with application version `1.29.1`. This release has
no database migration or API contract change. SQLite remains the default; the
optional PostgreSQL backend retains its existing configuration and
single-application-replica boundary.

Before updating trusted-proxy installations, confirm that the observed proxy
socket source is covered by `TRUSTED_PROXY_CIDRS` and that
`OIDC_USER_ID_HEADER` contains a stable provider subject. Follow the current
[configuration guide](../configuration.md) and [update guide](../update.md).

The release is promoted to `testing` for published-image acceptance.
`production` and `latest` require separate approval and remain unchanged by the
testing promotion.
