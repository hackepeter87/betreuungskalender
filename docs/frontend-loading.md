# Frontend loading and offline behavior

The initial application bundle contains the dashboard and first-use setup. The
remaining pages load only when they are opened. They share one accessible
loading state and one generic failure state with an explicit reload action.

Report, analytics, and PDF generation dependencies stay outside the initial
bundle. The production build writes a Vite manifest and fails when a JavaScript
chunk exceeds 500 kB, when report or analytics code becomes eager, or when PDF
dependencies enter the initial import graph.

The service worker caches hashed frontend assets after they have been loaded.
This means a previously opened deferred page can be available from the
installed application cache. A page that has never been downloaded still
requires a network connection. API requests remain network-only, and offline
use remains read-only.

When a deferred asset cannot be loaded, the browser retains that failed module
URL for the current document. The failure state therefore offers an explicit
application reload instead of presenting an in-place retry that cannot recover
reliably.

## Appearance preference

Settings provides System, Light and Dark appearance. System is the default and
follows changes to the operating-system preference. An explicit choice overrides
the system until the user selects System again. The preference is stored only
in this browser under `betreuungskalender.appearance.v1`; it is not an account
setting, contains no domain data and is not sent to the server. Clearing site
storage restores the default. If storage is blocked, the control still works
for the current page, but its choice cannot survive a reload.

The same-origin `appearance.js` bootstrap runs before rendering the application
or public legal documents. It applies the saved preference without waiting for
React and updates browser/PWA theme metadata. Open tabs share preference changes.
The installed application caches this bootstrap alongside its shell. Legal
documents remain readable without JavaScript; in that case they follow the
system preference instead of a saved override.

Screen colors use standard CSS `color-scheme` and `light-dark()` support in
current browsers. Older browsers without these features are not a supported
appearance-mode target. Printing explicitly selects the light palette; PDF
generation uses its existing independent palette and is not affected by the
screen preference.

Browser tests use a loopback HTTPS origin with a short-lived, self-signed test
certificate generated by the test runner in a temporary directory. `scripts/e2e-server.mjs`
forwards requests to the unchanged production server on the next local port
while the runner removes its certificate on exit. This keeps the normal content-security
policy active in Chromium and WebKit. Only Playwright accepts the test
certificate. Chromium's test launch additionally pins that certificate's public
key for service-worker installation, without disabling general certificate
checks. No application TLS or authentication setting is changed. Running
the suite requires OpenSSL and both Playwright browser engines.
