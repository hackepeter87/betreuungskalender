# v1.25.0

`v1.25.0` aligns application contracts and recurring-rule behavior across the
browser and server while reducing unnecessary audit data loading.

## Consistent recurring rules and settings

- Contact-rule previews and server-side synchronization now use the same pure
  recurrence expansion for weekly, monthly, segmented, and multi-rule
  schedules.
- Existing occurrence keys, sorting, synchronized entries, conflict checks,
  and persisted data remain unchanged.
- Browser and server share one typed settings contract. Settings writes reject
  unknown fields, invalid values, and references to inactive care parties.
- Invalid historical setting values fall back to safe defaults without
  changing valid backups or portable transfer packages.

## Bounded audit and invitation responses

- The audit view loads stable cursor-based pages instead of receiving the
  complete history during application startup.
- Actor display-name lookup is limited to IDs already referenced by loaded
  domain data and does not return email addresses or identity-provider claims.
- The legacy audit endpoint remains available for one compatibility version
  with a fixed maximum result size.
- Invitation creation returns the complete one-time invitation URL and no
  longer exposes the underlying bearer token as a separate response field.
  Manual sharing, optional email delivery, and imported-actor invitations use
  the same URL.

## Compatibility and upgrade

Migration `032_audit_pagination_index` adds only an index for stable audit
pagination and does not alter existing records. Existing recurring rules,
settings, invitations, memberships, backups, portable transfers, and calendar
feeds remain compatible.

The Helm chart is updated to `0.6.0` with application version `1.25.0`.

## Validation

The release is validated with type checks, unit and integration tests,
responsive browser checks, runtime security tests, container and Helm smoke
tests, dependency analysis, CodeQL, and strict release checks. Published
artifacts are promoted only to the `testing` channel for separate runtime
acceptance. The `production` and `latest` channels remain unchanged.
