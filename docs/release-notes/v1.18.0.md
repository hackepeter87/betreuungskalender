# v1.18.0

`v1.18.0` makes care planning, confirmation, reporting, and recurring-rule
authoring follow one consistent workflow.

## Highlights

- Planned overlaps remain editable and are shown consistently in the calendar,
  agenda, and entry list so they can be reviewed deliberately.
- New completed or partial-care changes are rejected when they would overlap
  actual care for the same child. Adjacent intervals and entries for different
  children remain valid.
- Reports, CSV exports, PDFs, and holiday allocations merge duplicate
  same-party time and identify ambiguous cross-party overlap instead of
  silently crediting it twice.
- Mobile contact-rule authoring is divided into four focused steps for range,
  recurrence, time spans, and assignment. A live preview remains visible while
  a custom rhythm is configured.
- Care lifecycle actions are kept in the entry workflow. Contact rules remain
  responsible for recurrence, preview, synchronization, and exceptions.

## Existing data

- No database migration is added by this release.
- Existing entries, recurring rules, holidays, unavailability records,
  memberships, sessions, invitations, and calendar feed tokens remain
  compatible.
- Existing contradictory care entries remain readable and are not changed or
  deleted automatically.
- Historical reports can show different values where overlapping actual care
  was previously counted more than once. Ambiguous time is now shown as
  unresolved rather than silently assigned.

## API compatibility

- `GET /api/care-conflicts` returns `{ items, complete }`. `complete: false`
  keeps care entries available while clearly indicating that no complete
  derived overview could be produced within the processing budget.
- Writes that would create conflicting actual care return
  `409 care_entry_conflict` with a generic response.
- Existing routes and request formats remain compatible.

## Configuration

- Deployment environment variables are unchanged from v1.17.1.
- Update release references to `1.18.0` and keep the existing data and backup
  mounts writable by the container user.

## Validation

The release is validated with lint, unit and integration tests, production
build, browser tests on desktop, iPhone, and iPad profiles, runtime security
tests, strict release checks, container validation, CodeQL, and release
artifact checksum verification.
